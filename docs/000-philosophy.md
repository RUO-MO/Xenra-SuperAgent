# 000 理念

[English](000-philosophy.en.md) · 中文

Xenra-SuperAgent 是一个主动式编码智能体，也是一种与它一起工作的规矩。代码、面板和这份文档都按同一条原则取舍：

**尽可能少占用人的注意力，尽可能多交付价值。**

这条原则不是口号，它决定一个行为要不要做、一句话要不要发。一个通知如果只是在人已经知道结果之后再复述一遍，它占用的注意力就是净支出。因此这个智能体在没人要求的时候保持安静，在被要求之后做到可评审，然后回到原对话里说一句能让人行动的话。

## 对智能体的要求

- **只在被请求时行动，或只在写下来的条件下行动。** 请求必须明确指向智能体，并且来自允许名单上的人，或落在准入表为那个接收范围允许的情形里；其余消息只有通过准入表和接单模式才能成为候选。没人要求的工作需要团队写下的一条规则，并且默认从只记录、不实际接单的模式开始。
- **只在有人必须行动、或能用上结果时才说话。** 接单时用一句话确认要做什么；干活期间进展留在内部。结果可以评审、需要决定、或确实做不下去时才再次开口。消息要短：一条即时消息的上限是一百个词，链接和链接文字都算在内。
- **一次只问一个具体问题。** 问题走结构化字段，回到提出它的那条消息所在的对话，而不是埋在报告的正文里等人自己发现。
- **按影响停下，而不是按工作量停下。** 局部改做到底，交付一个可评审的结果；需要改动公开接口、改变模块职责、或需要人做设计决定时，带着一个明确的问题停下，并保留一份说明未完成原因的草稿。
- **如实汇报。** 草稿标明未完成，失败就报失败，没有真实的前后对比证据就不算就绪，更不会为了回避提问而绕开限制或伪装成功。

## 对设计的要求

- **概念要少。** 模型里只有领域本身需要的概念——来源、触发、线程、策略、评估、决定、授权、工单、派工、输入、报告、待人工决定——以及它们在具体来源上的实现。一个业务需求要么成为某个概念的属性，要么成为智能体遵循的提示词，设计不为它新增概念。
- **设置要少。** 当一个值几乎适合所有团队时，用默认值代替设置项；团队用文字描述的行为属于提示词，不属于设置。只有代码必须强制的东西——允许名单、规则、接单模式、并发、执行目录与准备命令——才成为设置。
- **面板只显示需要人处理的事。** 它首先列出等人处理的内容；健康状态不占版面，数字只在会改变人的行为时才出现，并且等于它所链接的列表长度。
- **文档按顺序阅读。** 每篇编号文档只建立在它之前的文档之上，读者不需要用到尚未介绍的概念。

## 责任

智能体使用的账号，是团队每天都会看到的账号；它在这些账号下评论、开 Pull Request、给人发消息。它发出的每条消息都在消耗同事的注意力，这份责任由你承担。智能体能做的事越多，运营者该为团队付出的谨慎就越多：

- **从小处开始。** 先用一份很短的允许名单，让主动工作只记录不接单；等它本来会做的事看起来对了，再逐步放宽。
- **为减少噪音而调优。** 智能体太吵时，把它的提示词写得更短更严，或者把它停掉；不要增加更多消息去解释噪音。
- **不要用它制造产量。** 批量 PR、群发消息和没有下文的忙碌，让团队付出的比得到的多。
- **为它说的话负责。** 读一读智能体以你的名义发布的内容；错了就去改提示词或规则，而不是事后逐条道歉。
- **管住自己的能力边界。** 合并、审批、访问权限这些决定，用提示词和仓库规则写清楚；默认让人来合并 Pull Request。

目标是：在对的时候给出对的帮助，其他时候什么都不说。
