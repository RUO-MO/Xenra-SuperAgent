# 002 授权

[English](002-authorization.en.md) · 中文

授权决定谁可以发起工作，以及这份工作可以包含什么。本文档建立在 [001 领域模型](001-domain.md) 之上，描述生成授权的那条路径：准入、研判、决定，以及授权在什么条件下失效。

准入由代码执行，提示词改不了它。消息、评论和被引用的文档只是判断的输入，它们无法提升强度，也无法改变允许名单。

## 触发的两条路径

### 评估：决定是否开始工作

来源记录一条消息是否针对智能体：`mention` 表示 @ 了机器人或智能体账号，`direct` 表示私信。人发的消息由准入按下面的顺序判断，第一个成立的规则决定它的归宿：

1. 发送者在来源的允许名单上，并且针对智能体发言：明确请求。
2. 它落在某个接收范围的准入单元格上，该单元格设成明确请求：明确请求，即使发送者不在名单上、即使线程上已有工单。
3. 它发在一个已经有工单的线程上（仅作上下文关注的订阅不算），并且不是名单外的人发来的私聊：后续发言，强度取明确（发送者在名单上）或推断（不在名单上）；接单模式为 `off` 时，只有名单上的人能走这条。
4. 它的准入单元格设成推断候选，且接单模式不是 `off`：推断候选。
5. 其余一律不予准入，理由按代码给出：发送者不在名单上（`not_a_member`）、准入表忽略（`admission_ignored`），或没有指向智能体（`no_mention`）。

机器人走另一套判定：只有来源机器人名单上的机器人能产生推断候选，条件是要么针对智能体发言，要么落在来源接收全部消息的范围里；其他机器人的消息不予准入。没有发起者的系统事件，例如 CI 结果，只查它所在范围的"不在名单上、未针对智能体"单元格，且只在接单模式不是 `off` 时准入。机器人永远不能构成明确请求，也永远不能停止工单。

"接收全部消息"指来源观察到了这条消息：飞书群里设为 **全部消息**，或 GitHub 打开了对应的全量接收开关。未针对智能体的消息只在这样的范围里才进入系统，因为来源根本不会把别处的它们送进来。

### 订阅：继续已有的工作

已订阅线程上的每条后续消息都会作为输入到达订阅它的工单，包括机器人和 CI 的消息。这条路径绕过准入，也不赋予任何新权限；每张工单仍受自己的授权约束。

人发在工单自己线程上的消息，归那张工单的执行器判断，不进入评估。主 Session 把一条消息挂到工单上时也一样。执行器持有该消息期间，它拿不到别的判定：接单、挂载与重新排队都会被拒绝，只有停止是例外。执行器要么在工单范围内处理这个请求，要么交回以便路由到别处。

归属关系在工单存活期间一直有效，即使有人移除了它在那个线程上的订阅。它同样覆盖已结束、但不是被人停止、且有待处理消息可以使它恢复的工单。

主 Session 会收到一条后续通知，通知里列出消息和它到达的工单。执行器持有该消息期间，主 Session 只能在人的要求下停止工作。

### 交回与释放后续

执行器发现请求超出工单范围、或属于另一张工单时，可以交回一次，并给出一句理由。工单保留自己的订阅。如果挂载进来的线程无关，执行器会在交回它在该线程上持有的消息之后放弃这个订阅；工单起始所在的线程和来源让它关注的线程不能被放弃。

只有当没有任何工单还持有这条消息时，它才会进入新的评估，它的候选带着执行器给出的理由。准入按该线程上一条普通消息判断它，主 Session 可以接单、挂到别处或忽略。交回一条工单本来就不持有的消息（例如机器人消息，或已经送进评估的消息）只会记录这次交回，不排队任何东西。

工单结束时，会释放执行器没有读过的后续消息，以及它读过、却没有确认、回答或交回的人的消息。只要没有其他工单持有它，每条被释放的消息都会进入评估。停止只结束被停止工单的工作，停止它的那条消息不会再被送进评估；主 Session 可以把这条消息的其余部分当作新工作接单。

人可以在面板上把人持有的后续消息送进评估。如果主 Session 随后又把它挂回一张活动工单，执行器会再次收到它。

### 仅作上下文的订阅

执行器可以关注一个相关的线程（例如另一个 Issue 或 Pull Request）作为上下文。该线程的消息会到达工单，但不赋予权限，也不带来后续强度；那里的人的消息不会使已结束的工单恢复，除非主 Session 挂载了它。主 Session 关于其他工作的备注同样只是上下文。

没有到达任何工单的人的消息（包括其工单被人停止的线程）走评估路径。机器人消息独立于它们已经送达已订阅工单这一点，同样走这条路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit（明确） | 名单上的人针对智能体发言；名单上的人在已有工单的线程上后续发言；准入表某个单元格设为明确请求 |
| inferred（推断） | 不在名单上的人在已有工单的线程上后续发言；准入表某个单元格设为推断候选；来源机器人名单上的机器人，其消息针对智能体或落在接收全部消息的范围里；没有发起者的系统事件落在设为推断候选的单元格上 |
| 不予准入 | 其他任何机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的所有推断情形 |

推断候选只在 `auto` 模式下才可能被接单，而且接单时命中的规则必须全部处于启用状态。`observe` 下正面研判的结果记为"本会接单"的忽略。

## 准入表

策略的每个来源部分都有一张准入表，它的行是接收范围：

- **飞书：** 每个已配置的群、机器人收到 @ 的其他群，以及私聊。其他群只有把卡片上的 **其他群** 设为 **仅 @** 时才有一行可用的单元格。
- **GitHub：** 新 Issue、新 Pull Request、评论，以及默认分支的 CI。

一行最多有三个单元格，每个单元格决定一条消息是变成明确请求、推断候选，还是什么都不做：

| 单元格 | 可选值 | 默认 |
| --- | --- | --- |
| 在名单上、未针对智能体 | inferred、ignore | inferred |
| 不在名单上、针对智能体 | explicit、inferred、ignore | ignore |
| 不在名单上、未针对智能体 | inferred、ignore | ignore |

单元格只在来源确实会收到这类消息时才可选：范围设为仅 @，前两个单元格里的"未针对智能体"那格就不可用；CI 没有发送者，所以它的行只提供最后一个单元格。机器人消息使用机器人名单，而不是这些单元格。

把"不在名单上、针对智能体"设为明确，就允许该范围内的任何人在 @ 智能体时请求工作；面板在这一格给出警告。这对专门的支持群有用，对仓库评论则意味着任何能评论的人都能开单。

准入表是策略版本的一部分。减弱某个单元格不会立刻停掉在该单元格下接单的活动工单；它在恢复前重新校验时可能被撤销授权。

### 机器人与自动评审者

宿主把以 `[bot]` 结尾的登录名、GitHub App 和飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，它们的消息可以成为推断候选；它们不能发出明确请求，也不能停止工单。

使用普通账号的自动评审者对宿主来说算作人：它的评论会到达已订阅的工单，并触发后续通知，因此也不受"每条 Pull Request 每个自动评审者最多三轮"这条提示词约定的自动约束。团队提示词必须把这类账号标明为自动评审者，评审轮的计数与拒绝理由都靠提示词执行。

## 候选的路由

主 Session 用 `orchestrator_route` 路由明确候选。一次调用最多二十项，每一项独立处理：某一项被拒绝或缺字段，不影响其余项执行。一项可以是：

| 种类 | 需要 | 效果 |
| --- | --- | --- |
| `accept` | `trigger_id`、`title`、`worktree_name`、`acknowledgement` | 对这条触发做一次接单决定，并创建工单；已经开过工单的触发返回原工单，标题与确认保持不变 |
| `attach` | `trigger_id`、`ticket_id` | 把触发挂到工单上：工单订阅它所在的线程，并把它作为输入收到；持有它的评估就此结束，同一批里的其他触发另起一次评估 |
| `stop` | `trigger_id`、`ticket_id` | 仅在准入给出明确强度时结束工单；否则记为忽略 |
| `ignore` | `trigger_id`、`reason` | 记录一次忽略，可用它忽略只凭卡片就能判断的主动候选 |

`worktree_name` 是 1 到 4 个英文小写短词、最长 32 个字符；`acknowledgement` 一句话、最多一百个词，以来源对话的语言书写。挂载与接单都可以带一条路由备注，最多三十个词（中文按分词计数）。

推断候选通常需要一次完整研判：`orchestrator_eval` 载入候选的窗口，`orchestrator_eval_read` 继续读线程、图片或仓库文件，`orchestrator_eval_decide` 记录判断。有一个捷径：卡片本身已经说明它不涉及任何启用的规则时，可以直接用 `orchestrator_route` 忽略它，决定会记下 `ignoredFromCard`，以区别于基于规则的研判。

接单一个推断候选永远要经过研判。直接接单一条准入未判定为明确的触发会被拒绝。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 作用 |
| --- | --- |
| `off` | 任何推断都成不了候选，例如未针对智能体的消息、机器人的消息，或不在名单上的人的后续发言 |
| `observe`（默认） | 对推断候选做研判；正面研判记为"本会接单"的忽略，不实际接单 |
| `auto` | 对推断候选的正面研判会直接接单 |

明确请求在任何模式下都有效。从 `observe` 开始，看过记录下来的决定之后再切到 `auto`。

每条规则描述一类主动工作，带名称与说明，最长两千个字符。研判对每条启用的规则恰好判断一次，无论是否命中；接单至少需要命中一条规则，而忽略与未完成的判断记录全部规则的判断结果。工单的授权记录命中的规则，它的执行器收到这些规则的名称和说明，这些说明对该工单的流程与沟通要求优先于默认值。适用于所有工单的要求应放进团队提示词小节。

研判还必须给出方向：是否要求实现、目标是有明确指定的还是已有既定标准、是否仍有未决的设计决定，以及支持这些判断的原话。方向未定或被要求做设计决定时，接单会被降级为忽略。

## 策略版本

规则、接单模式和每个来源的策略部分共同构成策略版本：它是对这三者的内容哈希，哈希的输入里带着 `mandate-v3` 这个修订号。每份授权都记录它是在哪个版本下被接单的。模型、并发、暂停状态、轮询间隔不属于策略版本：改它们不作废已经作出的决定。

版本变化会作废正在运行的评估：它们以 `unavailable` 结束并立刻按新版本重新排队自己的触发。同时给每个受影响的活动工单发送一条"策略已变更"的输入，说明：

- 命中的规则是否变了（附它现在的说明），或不再适用；
- 请求者是否已不能发起工作；或
- 主动工作是否已不再被接单，例如模式从 `auto` 改成了别的。

未受影响的工单不会收到通知。变更不会立刻撤销活动工单的授权，只影响它之后的判断与恢复。

来源配置与策略分开。它控制系统里进来什么：读哪些群，某个范围接收全部消息还是只接收 @。授权记录它的来源和接收范围。恢复要求来源仍在监听该线程，但不要求它仍接收那里的全部消息。

来源关闭期间，回复会等待；如果来源已不再监听它的目标，回复会被丢弃。

关于执行器可以用自己的结果做什么的条件（例如何时可以合并），并不决定谁可以授权工作。它属于提示词，不属于策略。

## 恢复与停止

已结束的工单保留它的授权。人发在它某个线程上的消息，无需新的评估或决定就能让同一份工作恢复，无论发送者是谁。机器人、CI 和仅作上下文的消息不会唤醒已结束的工单。执行器判断该请求是否符合范围，不符合就交回或结束这一轮。

只有三种操作会改变授权：接单创建它，人的停止撤回它，重新校验失败撤销它。被人停止的工单保持已结束，不再接收任何东西；在那里请求工作需要新的接单。

- **人在线程里说"停止"是一条普通触发，** 由评估判断是否停止；强度不明时它变成一次忽略。执行器不能声明有人要求它停止，只能把消息交回。
- **面板上的停止是一条命令。** 它直接作用于工单，记录为人工停止，不需要新的评估。
- **需要等待的条件属于来源。** 例如"N 小时无人认领"这样的条件，会是一个自己等待并再次检查的来源；评估从不等待。

### 恢复前的重新校验

来源必须仍在监听最初的线程，否则授权失效。其余检查取决于授权的依据：

- 明确的后续授权通过。
- 推断的后续授权需要 `auto` 模式，且它命中的规则仍然启用。
- 通过表格单元格准入的授权，必须按今天的表格与发送者成员关系仍能获得至少原有的强度。因此把发送者移出名单，可能撤销通过"名单内发送者"单元格接单的授权；把人加进名单则让原先的"不在名单上、未针对智能体"一格转为"在名单上、未针对智能体"后继续检查。
- 机器人的授权要求该机器人仍在来源的机器人名单上。推断的表格授权与机器人授权还需要 `auto` 模式以及仍启用的命中规则。
- 其他授权要求发送者仍在来源的允许名单上。

重新校验失败时，工单保持已结束，不接收任何等待中的消息。每条消息都被当作没有到达任何工单；如果没有别的工单持有它，它就进入评估。主 Session 不会被告知它到达过某个执行器。暂停处理之后也适用同样的规则。挂载到该工单会被拒绝，继续工作需要新的接单。

## 评估没有完成时

时限从候选到达主 Session 时开始计算，默认一百二十秒，可设三十到六百秒。等待送达的时间不计入，未送达的候选也永不过期。

超时的评估会把它的触发重新排队以便再试一次；连续两次如此之后，第三次超时记录 `unavailable`，理由是超时。研判自己报告 `unavailable`、按旧策略作出的判断、以及策略变更导致的作废，同样记为 `unavailable`；策略相关的情形会立刻按当前版本重新排队该批次。

`evals` 健康项报告最近一小时内未解决、且其线程之后再没有判断的 `unavailable` 决定；`scripts/xenra-superagent status` 会把该错误包含在内。总览按二十四小时窗口逐个列出这些未完成的评估。

只有当未完成的决定仍是其线程上最新的决定、尚未被忽略，且该线程既未排队也不在评估中时，总览才会请求人工处理。人可以重新评估该触发，或忽略这个问题。
