# 003 执行

[English](003-execution.en.md) · 中文

本文档沿一张已接单的工单，走过启动、交付与恢复。它建立在 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md) 之上。

## 工单阶段

每张活动工单只有一个阶段，由它在等待什么决定。从上往下读这张表，第一个匹配的行胜出。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 送达输入失败；2 秒后重试，之后延迟翻倍最多到一分钟，成功送达、新的派工或工单结束都会清除它 | 输入未送达 |
| person / answer | 它有"待人工决定" | 待回答 |
| person / review | 最新报告是 `ready` | 待验收 |
| person / blocked、failed | 最新报告是 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | 待处理受阻 · 待处理失败 |
| working / queued | 没有派工，或派工处于 pending | 排队中 |
| idle | 最新报告是 `waiting`，或派工已结束 | 等待新触发 |
| working | 其余一切 | 执行中 |

`person` 阶段意味着工单没有人的输入就无法继续。新的人的消息会把 `blocked` 或 `failed` 的工单交还给它的执行器，因此它会移到下一个匹配的阶段，通常是 `working`。

`idle` 的工单已经结束该轮，且没有悬而未决的问题。已订阅线程上的触发可以使它继续。

## 执行器

每张工单得到一个名为 `worker-<工单 id>` 的执行器 Session，以及一个以工单短名开头、后接工单 id 前十二位的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以运营者的操作系统用户身份、在 `danger-full-access` 权限下运行。它们使用 `xenra-superagent-worker` 预置：DeepSeek Harness 的 `standard` 预置加上完成工单所需的工具，并把前台命令在 5 秒后转入后台作业。这样执行器可以在下一步收到新消息，而不必等一条长命令跑完；作业结束时反过来唤醒它。

主 Session 使用 `xenra-superagent-router` 预置，没有 persona，提示词全部由 Xenra-SuperAgent 组装。它的工具白名单只有六项：`skill`、`read`、`read_image`、`job_output`、`job_list`、`job_kill`，并且只保留 profile 实际注册的那些——用 `pwsh` 的机器没有 `bash`，没有作业服务的 profile 没有后三项。它没有写文件、改文件、shell 和联网工具。预置里声明的 shell 与作业等待仍是 5 秒上限，另外一道守卫会拒绝 `sleep`、超过 30 秒的 shell 超时和超过 5 秒的作业等待。

Session 保持创建时选定的预置。执行器 Session 被外部删除后，下次交付会按同一 id 重新建立。

执行器拿到的工具是这份白名单，并且只保留 profile 实际注册的那些：`read`、`write`、`edit`、`read_image`、`glob`、`grep`、`bash`、`pwsh`、`job_output`、`job_list`、`job_kill`、`web_search`、`web_fetch`、`skill`、`todo_write`、`subagent`、`list_subagent_models`、`send_message`、`list_agents`、`interrupt_agent`。随机附带的预置打开了联网检索但关掉了网页抓取，因此在这样的 profile 上 `web_fetch` 不会出现；profile 里其他任何工具都拿不到：向人提问或展示、修改配置、安排定时任务、编辑文档的工具一律排除。工单结束后这道限制依旧生效：工具调用会被拒绝，并说明新工作需要通过新的工单。

执行器的子智能体（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预置和执行器的权限，保留同一份工作工具；它们通过 `listDescendants` 列出、通过 `drainDescendants` 释放，子智能体自己的作业在它结束时被终止。在 `standard` 下，shell 命令超过 60 秒才转入后台。

### 后台工作与执行器槽位

当一轮结束、报告仍是 `progress`，且仍有 shell 作业或子智能体在运行，工单保留它的执行器槽位并保持"执行中"。它不会被报告为等待，主 Session 也不会收到等待报告。作业或子智能体完成时会唤醒执行器，而这一次唤醒的回合结束时又会重新检视。

每轮之后，后台工作最多有 30 分钟完成。到达该上限时，仍在运行的 shell 作业被终止，工单报告为等待。报告带上执行器最后的原话，以及哪些作业被终止，或子智能体仍在运行。子智能体允许继续，下一轮会读到被终止作业的结果。

移交给人时立刻释放槽位，并让报告继续生效：这适用于 `ready` 报告或提出问题之后（除非此后又到达了输入），也适用于任何 `blocked` 或 `failed` 报告之后。移交时子智能体被释放；shell 作业（例如为评审而起的服务）交给那个人继续运行，直到派工结束。它们不占槽位，也不受 30 分钟限制，后续回合之后也一样。它们结束时不会唤醒执行器，执行器在下一轮读取结果。

人也可以直接在执行器 Session 里写话来开启一轮；这一轮的结束与后台工作遵循同样的规则。

派工结束时，它的 shell 作业被终止且不唤醒 Session；它的子智能体被释放，它们唤醒的回合也会被丢弃。替代的派工和它等待中的输入在关闭完成后才开始。停止或重启插件走同一条路径：关闭时每个执行器最多等 10 秒，尚未进入 Session 历史的输入会保留。

### 准备工单目录

在第一次派工之前，如果工单目录不存在，prepare 命令会在它的父目录（默认就是执行根目录）里用 `sh -c` 运行一次，并带上这张工单的执行变量。它有十分钟完成。命令失败会删除它留下的空目录，并让工单失败、记录其输出；这次失败不会被自动重试，因为一个已存在的目录会被当作已准备好，重试会把失败的半成品当成本地环境。人发的消息、重试或状态请求会再次尝试准备。

没有 prepare 命令时，执行器在空目录中开始。典型命令用 `git worktree` 创建检出。准备完成后目录还会被检查：如果仓库本地或 worktree 级的 git 配置里定义了 `credential.*` 或 `http.*extraheader`，准备失败，因为智能体的 git 也会读到它们。

一张 Pull Request 属于某张工单，当它是工单最初来自的那张，或者是智能体账号从"分支最后一段等于工单短名"的分支开出来的。前一种情况之外，一张 Pull Request 同时只能属于一张活动工单。

### 并发

工单从启动开始（包括准备阶段）、或从唤醒其空闲执行器的那次送达开始，持有一个执行器槽位。它在整个活动回合中也一直持有该槽位。

配置的并发上限（`maxWorkers`，默认 3，可设 1 到 16）作用于这些槽位，另外为人发的消息保留一个额外槽位。正常槽位占满时，人的消息可以使用额外槽位，并在新启动之前优先取得下一个空闲槽位，因此新工作不会挡住人继续已有的工单。

其他输入（例如 CI 结果）等待正常槽位。启动在 `working / queued` 中等待，直到有槽位空闲。多个启动并发进行，所以一条慢的 prepare 命令只会拖慢它自己的工单。

### 执行变量

prepare 命令和执行器说明收到同一组执行变量。命令读取环境变量；执行器在提示词里读到每个变量的值和说明。其中不含任何凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `XENRA_SUPERAGENT_DIR`、`XENRA_SUPERAGENT_NAME`、`XENRA_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `XENRA_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行环境禁止调用的程序，以空格分隔 |
| `XENRA_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，`owner/name` |
| `XENRA_SUPERAGENT_GITHUB_ACCOUNT`、`XENRA_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `XENRA_SUPERAGENT_GITHUB_NUMBER`、`XENRA_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起该工单的 Issue 或 Pull Request 编号；是 Pull Request 时还包括它的 head 引用 |
| `XENRA_SUPERAGENT_FEISHU_BOT`、`XENRA_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及发起该工单的群 |

工单专属的值来自它的目录和发起它的触发，其余来自当前部署设置。只有面板可以修改执行目录、准备命令与禁止调用的命令；主 Session 的文本改动会被拒绝。来源关闭时，它登记的变量不出现在执行环境里，但仍列在面板的变量表中，并标明来源已关闭。

执行器通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书，这两个名字由状态目录里的包装脚本重定向到配置的 CLI。被禁止的命令在按名字调用时直接失败；`gh`、`git` 和 `lark-cli` 不能被禁止。这些包装脚本、隔离的 git 配置和目录建立的是默认值与防误用的护栏，不是安全边界：执行器仍可以按绝对路径执行程序。

## 合并

自动合并完全由 **交付要求** 这段提示词管辖，宿主里没有专门处理合并的逻辑。

默认说明不允许以智能体账号开启自动合并，因为 GitHub 会把合并记在开启它的账号名下；它要求写明另一个账号的 CLI 用于合并。没有它，就由人来合并 Pull Request。

默认说明只允许对为该工单开启的 Pull Request 启用自动合并，条件是它已就绪、所需批准覆盖 head 提交、且改动行数（新增加删除）少于 200 行。在推送又一个修订之前，执行器会撤回自动合并，等条件对新 head 再次成立后重新开启。

没有正文的评审（例如批准）同样会作为触发到达，并能唤醒正在等待评审的执行器。这些说明约束的是智能体，而不是 GitHub 的合并规则。要强制批准，请在分支保护里要求批准并作废旧批准。省略合并 CLI 或删掉自动合并那段，就要求人工合并。

## 工单如何结束

- **就绪且没有跟随的线程：** `ready` 报告使工单以 completed 结束。
- **无事可做：** 执行器发现没有需要人处理的工作时（例如请求无法复现、不是缺陷、决定已在别处跟进）报告 `dropped`。工单静默结束，不发送消息，除非命中的规则要求发送；人之后在其线程上的消息会使它恢复。
- **被人停止：** 面板上的停止或一次明确的停止决定，以 stopped 结束并撤回授权。

### Pull Request

执行器报告之后，工单会跟随它起初来自的那张 Pull Request。它也会跟随智能体账号从工单分支开出的 Pull Request——无论是执行器报告的，还是 GitHub 来源轮询发现的。重新打开的 Pull Request 会再次被跟随；放弃订阅某个线程也会停止跟随它。

当它自己开启的 Pull Request 都不再打开时，工单完成。如果它没开启过任何 Pull Request，那么它跟随的所有 Pull Request 都必须关闭。随后它按最后一次相关关闭的结果结束（merged 或 closed），并保留订阅，使之后的人的评论能恢复它。

恢复、重试或恢复中的工作尚未完成时，关闭不会结束工单：若执行器确认或回答了它持有的后续消息，但此后尚未作出非进展报告、也没有在读过该消息后结束一轮，关闭会等待；若工单在关闭之后才恢复，则要等这次派工报告 `ready`。之后的 `ready` 报告在满足同一套规则后结束工单。

聊天渠道会收到一条关于 Pull Request 结果的最终通知（GitHub 渠道除外，Pull Request 本身已经显示了结果）。因此"待验收"通常意味着：有一份 `ready` 报告，且带着 Pull Request。

### 后续与上下文线程

执行器判断发生在其工单自己线程上的人的后续消息。它处理范围内的请求，把超出范围或属于其他工单的请求交回，交回后不再回答它，也不确认它。一旦没有执行器持有该消息，它就成为主 Session 的候选。除此之外，主 Session 只能按人的要求停止工作。

输入在 Session 把它纳入某一步、并随后作出报告或结束一轮之后，才算已读。工单结束时，未被确认、未被回答、也未被交回的未读消息会回到评估，如 [002 授权](002-authorization.md) 所述。已读但无需行动的消息（例如道谢）不会。

仅作上下文关注的线程仍会送达消息，但不赋予工单对后续消息的归属，也不会使已结束的工单恢复。这些消息可以独立地接受研判。

只要还有活动工单在订阅，来源就会轮询已订阅线程；并持续到最后一个触发与该订阅工单结束之中较晚者之后两周。此后消息只通过普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（记为 `failed`）时，工单不接收任何自动输入：CI 和机器人的消息会记录在它上面，但不送达、也不唤醒 Session。

模型服务或网络的一次性故障（HTTP 408、429、5xx，或连接被拒绝、被重置、超时、主机无法解析）最多重试三次：失败的一轮执行器会按 15 秒、30 秒、60 秒的退避被要求继续；失败的启动交给存储的工作队列重试（间隔从 5 秒起翻倍到 5 分钟），三次之后把工单标记为失败。失败的 prepare 命令不重试。

它的工具仍然可用，人可以直接在该 Session 里继续。失败的启动不会自行重试。

人的消息、之后既不是 `blocked` 也不是 `failed` 的报告、或一次重试，都会解除该暂停。暂停由存储的报告和输入推算得出，因此重启之后仍然存在。

### 重试

在活动工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：一次新的派工会结束当前派工、在同一执行器 Session、目录、分支和 Pull Request 上开启新的派工，并接收等待中的输入，这三者都靠它解决。主 Session 也可以在人明确要求时执行同样的操作。

一旦人的消息到达了受阻或失败的工单，执行器就持有该消息，因此工单显示为执行中（启动失败重新开始时显示为排队中），并且不再提供重试——除非送达该消息本身失败了。

执行器模型只在创建 Session 时生效；已有 Session 保持它原来的模型。

### 重启

正在运行的派工会以 `hostRestarted` 结束，新的派工带一份恢复说明开始，要求执行器在重复任何外部操作之前，先检查它的目录、git 历史和 GitHub 状态，最早的工单优先。

处于等待、就绪、受阻或失败状态的派工保持原样，除非在该报告之后有输入到达它们；那样它们也会重新开始。

Session、目录、订阅、待发消息以及下面存储的工作都能熬过重启。"每个执行器 Session 把哪些输入纳入了历史"这份记录也一样：一步在认领消息之后、调用模型之前只记一次；被重启切断的那一轮纳入的消息，只要之后有报告或一轮结束，就算已读；而未进入历史就被取消或错误切断的消息，算未读。

重试或重启会把被替代的派工收到、而其执行器 Session 未纳入的输入再次交给新派工；仍留在 Session 里等待的那一份，无论由重启保留还是跨崩溃持久化，都会在新派工的第一条消息之前被移除，使新送达成为唯一的副本。

### 存储的工作

Xenra-SuperAgent 在作出决定之后要做的事——把候选、后续或报告转达给主 Session，启动派工，送达输入，发出消息——先写进状态目录里的队列，然后再执行。这一点在内核命令的事务里完成，所以在崩溃后不会只剩一半。

转达、通知、评估送达与输入送达失败时（例如它的 Session 无法到达），会在 2 秒后重试，之后延迟翻倍最多到一分钟；启动派工与发送消息从 5 秒起重试，最多到 5 分钟。启动本身遇到一次性故障时在自己的处理里重试三次，仍失败则把工单标记为失败；处理暂停或暂时没有空槽位不算失败，只是按启动的退避再排一次。

每种工作只有在连续三次失败之后，才会在总览的系统问题里报错；输入送达失败则显示在它自己的工单上，不占系统的版面。

发往主 Session 的转达与通知保持顺序，一条失败会挡住同类的后续项；回复一次只发一条，按入队顺序执行。排队中的同一条消息被再次请求覆盖时，保留它的队列位置。

### 来源失败

GitHub 来源独立读取每个 Issue、Pull Request 和线程：读取失败会把错误留在该线程上，下次轮询再读，并计入来源的错误——默认连续三次轮询失败后报出；任何一次成功轮询都会重置计数。

智能体失去对私有仓库的访问时，GitHub 也会返回 404，所以 404 会重试。

被通知的 Issue 或 Pull Request 若读取持续失败，会在首次失败读取之后一天被丢弃；GitHub 返回 410 时则立即丢弃。此后它不再使轮询失败，它的线程保留错误，来源状态会点名它。

它的读取位置停在原处，因此之后的通知或对其线程的轮询会读到失败的读取漏掉的内容。

飞书事件消费者报告每一次失败；对已订阅话题的轮询把每次失败留在其线程上。列表或分页中的畸形条目会被跳过，来源状态会计入它。

### 渠道失败

发出的消息作为存储的工作排队，退避从 5 秒起重试，翻倍最多到 300 秒。

工单发往同一个会话的消息按入队顺序发出，因此它的确认会早于之后的回答或结果：同一工单发往同一会话的某条早前消息尚未发出时，后面的消息会等待，直到那条连续失败三次并显示为问题。

其他工单的消息、以及无工单的消息，不会为它等待。

有失败尝试的消息在发出或被撤回之前，都算系统问题。

只有当来源已不再监听该会话、或来源回复该会话永远无法收到时，消息才会被丢弃；来源关闭期间，它会等待。GitHub 上已删除的 Issue 或已锁定的会话，以及飞书上被撤回或已找不到的消息，来源都会给出这样的回答。针对已不存在的 review 评论的回复，改为发到 Pull Request 的会话。

被丢弃的消息保留记录，写明何时、为何被丢弃，以及它原本属于哪张工单，因此不会再被排队；被丢弃的确认显示为"已丢弃"，而不是"已发送"。

### 暂停处理

暂停会停止派发、新的评估、评估超时、输入送达和回复；已经开始的一次启动会等到处理恢复。

来源继续记录触发，正在运行的执行器轮次不会被打断。

人发给已结束工单的消息会等待：暂停结束后的第一次执行会恢复该工单，前提是它的授权在当时的策略下仍然成立。

进行中的评估在暂停期间不会过期；它的截止时间会按暂停时长顺延。

### 无效配置

来源种类拒绝的已存储来源配置会禁用那个来源实例，直到面板保存一份可用的配置。它已经产生的线程、工单和读取位置都保留。
